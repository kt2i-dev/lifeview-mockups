Review checklist

Check your screen against this before handing it off for review. It follows the LongBeachAdmin UI/UX Guidelines. Where the mockups were decided differently (pager label, the plain “Add” button, Effective Date on Add, blank null dates), this list follows the mockups.

  • Structure
  • Name follows the convention (<Thing>Detail, <Thing>_Detail, <Thing>_Popup, Is…/Can… flags), and the screen or block description is current. Renames are reported (they change the URL).
  • Right pattern for the endpoint: Editable (PUT), Add-only (POST, no PUT) or Read-only (GET only). Detail and edit are one block, never a separate edit screen.
  • Read-only fields are plain text in the same position in both modes. No disabled inputs standing in for read-only.
  • Add opens the same block already in edit mode (empty key) and loads dropdowns from /options or /v1/codes, not the detail GET.
  • Cancel on an existing record resets and leaves edit mode; Cancel on a new record goes back to the list. A successful Save goes back to the list or tab.
  • Fields
  • No typed asterisks: required markers come from Mandatory and show only while editing.
  • Max length matches the bound attribute; number input type for decimals and currency.
  • Coded fields use CodeTableDropdown (from /v1/codes/{table} or the GET’s *Options), with a plain label beside it and its selected-code handler wired. Fields with no code table are plain text inputs.
  • No value repeated from the title or the header card.
  • Dates use the format MM/dd/yyyy, exactly that (capital MM, lowercase dd and yyyy): it’s the mask the OutSystems date formatter expects. Null dates (none, or 01/01/1900) are blank everywhere, never N/A or the placeholder date. Currency has 2 decimals; SSN and other masked IDs show last 4 only.
  • Saving and errors
  • Save sends every field the form shows, including blanks, and passes colToken back unchanged.
  • Effective Date never defaults to CurrentDate(). On Add, leaving it blank lets the gateway use the current pay period begin date (as the mockups say).
  • Save is disabled with a busy state (“Saving…”) while the request runs.
  • Errors show one alert: detail as the main line, then hostCode – hostMessage on a smaller line when hostCode isn’t null.
  • 409: tell the user the record changed and reload it. 422 with TS0122: confirm, then re-send with overrideExceptions=true. 403: show the error, nothing saved.
  • Delete asks first and names the record (“Delete deduction 068 effective 08/08/2026?”).
  • Lists and data
  • Shared table style and heading class (heading5); row buttons are the outlined “Details” (and “Accumulator”) blocks; the list button says “Add”.
  • Empty list shows “No items to show”.
  • Gateway lists use the APIPagination block (Previous · Page n · Next, “Page n of n” on the last page; Next from hasMore). Aggregates use the standard OutSystems pagination.
  • Filters: Search (primary) and Reset (secondary) in the shared filter-actions container.
  • Data comes from data actions with Fetch at start, never a server action in the initialization action. A loading state shows while each one runs.
  • Calls go to the persona’s own gateway endpoints (HR, Payroll, Benefits), not new calls to the Employee folder’s actions.
  • Styling and hand-off
  • No inline styles: OutSystems UI utility classes first, else one named theme class. No new accr- classes.
  • No new validation warnings.
  • Checked in the browser yourself, and a browser check requested for any visual change.
