Review checklist

Check your screen against this before handing it off for review. It follows the LongBeachAdmin UI/UX Guidelines, except where the mockups were decided differently since: the pager label, the plain “Add” list button, Effective Date on Add, blank null dates, the sticky header with Delete | Cancel · Add · Update, and the exceptions toggle in place of the TS0122 dialog. There, this list follows the mockups.

  • Structure
  • Name follows the convention (<Thing>Detail, <Thing>_Detail, <Thing>_Popup, Is…/Can… flags), and the screen or block description is current. Renames are reported (they change the URL).
  • Right pattern for the endpoint: Editable (PUT), Add-only (POST, no PUT) or Read-only (GET only). Detail and edit are one block, never a separate edit screen.
  • Layout follows the Details/Edit Screen Template: ds-root, one ds-card per section with its ds-card-title, fields in a Grid container (1 / 2 / 3 columns; column gap M, row gap Base, set on the container), each field a ds-field with ds-label and ds-value.
  • A sticky header row: title left, actions right. View: Back · Edit. Editing: Return | Override Exceptions · Delete | Cancel · Add · Update (Add only where LifeView has both). Adding: Return | Override Exceptions · Cancel · Add.
  • Read-only fields are plain text in the same position in every mode. No disabled inputs standing in for read-only.
  • Add opens the same block already in edit mode (empty key) and loads dropdowns from /options or /v1/codes, not the detail GET.
  • Cancel on an existing record resets and leaves edit mode; on a new record it goes back to the list. A successful Add or Update goes back to the list or tab.
  • Fields
  • No typed asterisks: required markers come from Mandatory (CodeTableDropdown: IsRequired) and show only while editing.
  • Max length matches the bound attribute; number input type for decimals and currency.
  • Coded fields: CodeTableDropdown (IncentiveCodeDropdown for incentive codes) in the edit branch only, drawing its own label, with CodeSelected wired. In View, a ds-field whose ds-value is the description field the GET returns. CodeTableText only in the HR1 and New Hire requests, never in EmployeeManagement. No description field: build the text from the code. No code table: a plain text input.
  • No value repeated from the title or the header card.
  • Dates use the format MM/dd/yyyy, exactly that (capital MM, lowercase dd and yyyy): it’s the mask the OutSystems date formatter expects. Displayed dates use the DateExpression block. Null dates (none, or 01/01/1900) are blank everywhere, never N/A or the placeholder date. Decimals and currency: FormatDecimal(value, 2, ".", ","). SSN and other masked IDs show last 4 only.
  • Saving and errors
  • Update (PUT, this record) and Add (POST, a new row) send every field the form shows, including blanks, and pass colToken back unchanged.
  • Add and Update are normal buttons in the form (they run its validation), with Button Loading: a busy state and disabled while the request runs.
  • Return | Override Exceptions on every screen whose endpoint takes overrideExceptions: Return by default, reset when the form opens and after each save; Override sends ?overrideExceptions=true.
  • Effective Date never defaults to CurrentDate(). On Add, leaving it blank lets the gateway use the current pay period begin date (as the mockups say).
  • Errors show one alert above the first card, and the page scrolls to it: detail as the main line, then hostCode – hostMessage on a smaller line when hostCode isn’t null.
  • 409: tell the user the record changed and reload it. TS0122 sent with Return Exceptions: the alert has an “Update with Override Exceptions” (or “Add …”) button, one click, no dialog. 403: show the error, nothing saved.
  • Delete asks first and names the record (“Delete deduction 068 effective 08/08/2026?”).
  • Lists and data
  • Shared table style and heading class (heading5); row buttons are the outlined “Details” (and “Accumulator”) blocks; the list button says “Add”.
  • Loading and empty states come from APIPagination (spinner; “No results found matching search criteria.”).
  • Gateway lists use the APIPagination block (Previous · Page n · Next, “Page n of n” on the last page), and the call sends its StartIndex as skip and PageSize as pageSize. Aggregates use the standard OutSystems pagination.
  • An Effective Date filter is the EffectiveDateFilter block. Other filters: Search (primary) and Reset (secondary) in the shared filter-actions container. A filter change goes back to page 1.
  • Data comes from data actions with Fetch at start, never a server action in the initialization action. A loading state shows while each one runs.
  • Calls go to the persona’s own gateway endpoints (HR, Payroll, Benefits), not new calls to the Employee folder’s actions.
  • Styling and hand-off
  • No hex colors. Colors come from the theme: primary, secondary, info / success / warning / error (each with -light), neutral-0–neutral-10, as classes (text-error, background-warning-light) or variables (var(--color-primary)). There’s no “alert” color: use warning.
  • No pixel values. Spacing uses the theme’s steps (xs 4, s 8, base 16, m 24, l 32, xl 40, xxl 48) through classes like margin-base, padding-top-s, margin-y-m, or var(--space-base). Type: heading1–heading6, font-size-base / -s / -xs, font-semi-bold, font-bold. Corners, borders and shadows: border-radius-*, border-size-*, shadow-*. Full list in the Details/Edit Screen Template.
  • No inline styles: an OutSystems UI utility class first, else one named theme class built from those variables. Side-by-side layout from the containers’ layout properties, not custom flex or grid. No new accr- classes.
  • No new validation warnings.
  • Checked in the browser yourself, and a browser check requested for any visual change.
